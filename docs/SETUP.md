# Prerequisites Setup Guide

This guide covers everything needed **before** opening the study repository for the
first time: running SQL Server in Docker, downloading the OMOP vocabulary from Athena,
and wiring the dev container to both.

---

## System requirements

| Requirement | Minimum | Notes |
|-------------|---------|-------|
| Docker Desktop | 4.x | [docker.com/products/docker-desktop](https://www.docker.com/products/docker-desktop/) |
| VS Code | Latest | [code.visualstudio.com](https://code.visualstudio.com) |
| Dev Containers extension | Latest | `ms-vscode-remote.remote-containers` |
| Free disk space | ~35 GB | ~5 GB vocab CSVs + ~25 GB loaded into SQL Server + ~2 GB Docker image + ~3 GB R packages |
| RAM | 8 GB | 16 GB recommended for vocabulary load |
| Internet | Required | Initial Docker image pull + Athena download |

> **Apple Silicon (M1/M2/M3):** The `mcr.microsoft.com/azure-sql-edge` image used here
> is built for `linux/arm64` and runs natively without Rosetta. Standard `mssql/server`
> images also support ARM64 since SQL Server 2022.

---

## Required folder layout

The dev container uses **relative paths** to locate the SQL Server container and the
vocabulary files. All pieces must live under a single parent folder (called `OMOP_Dev/`
here, but the name is yours to choose):

```
OMOP_Dev/                        ← parent folder (create this once, reuse for every study)
  .env                           ← SA password — NEVER commit this file
  docker-compose.yml             ← SQL Server container definition
  omop_vocab/                    ← Athena vocabulary CSVs — NEVER commit this folder
    CONCEPT.csv
    CONCEPT_ANCESTOR.csv
    CONCEPT_SYNONYM.csv
    CONCEPT_RELATIONSHIP.csv
    CONCEPT_CLASS.csv
    DOMAIN.csv
    DRUG_STRENGTH.csv
    RELATIONSHIP.csv
    VOCABULARY.csv
    CONCEPT_CPT4.csv             ← generated by the CPT-4 rebuild step (see below)
    cpt.sh / cpt.bat             ← CPT-4 rebuild scripts (included in the Athena download)
    cpt4.jar                     ← CPT-4 rebuild utility (included in the Athena download)
  <your-study>/                  ← study repository (one per study)
    config.R
    study_params.yaml
    ...
```

**Why the parent folder matters:**
The root workspace dev container compose declares:

```yaml
volumes:
  - ..:/workspace:cached          # mounts the study repo at /workspace
  - ../../omop_vocab:/omop_vocab  # mounts OMOP_Dev/omop_vocab/ read-only
env_file:
  - ../../.env                    # reads OMOP_Dev/.env for the SA password
```

These mounts are provided by the root workspace container configuration, so keep your study repository inside the workspace root as documented.

## Step 1 — Create the OMOP_Dev folder and .env file

```bash
mkdir OMOP_Dev
cd OMOP_Dev
```

Create a `.env` file with the SQL Server SA password. The password must meet SQL Server
complexity requirements (≥ 8 characters, mix of upper, lower, digit, and symbol):

```bash
# macOS / Linux
echo 'MSSQL_SA_PASSWORD=YourStrong@Passw0rd' > .env

# Windows (PowerShell)
'MSSQL_SA_PASSWORD=YourStrong@Passw0rd' | Out-File -Encoding ascii .env
```

> **Do not use `!` in the password.** Bash treats `!` as a history expansion character.
> Symbols like `@`, `#`, `$`, `%` work fine.

This file is intentionally outside the study repo and should **never** be committed
to version control.

---

## Step 2 — Create and start the SQL Server container

Create `OMOP_Dev/docker-compose.yml` with the following contents. This file also lives
outside the study repo so it can be shared across multiple studies on the same machine.

```yaml
version: '3.9'

services:
  mssql:
    # azure-sql-edge provides native linux/arm64 support for Apple Silicon.
    # Swap for mcr.microsoft.com/mssql/server:2022-latest on amd64 hardware.
    image: mcr.microsoft.com/azure-sql-edge:latest
    container_name: mssql_dev
    restart: unless-stopped
    ports:
      - "${MSSQL_PORT:-1433}:1433"
    environment:
      ACCEPT_EULA: "1"
      MSSQL_SA_PASSWORD: "${MSSQL_SA_PASSWORD}"
    volumes:
      - mssql_data:/var/opt/mssql
    healthcheck:
      test: ["CMD-SHELL", "bash -c 'cat /dev/null > /dev/tcp/localhost/1433' || exit 1"]
      interval: 15s
      timeout: 10s
      retries: 5
      start_period: 30s
    networks:
      - omop_dev_network

volumes:
  mssql_data:
    name: mssql_dev_data

networks:
  omop_dev_network:
    name: omop_dev_network
```

Start the container (run this from the `OMOP_Dev/` folder):

```bash
docker compose up -d
```

The first run pulls the image (~600 MB for Azure SQL Edge). Subsequent starts are fast.
Wait ~30–60 seconds for SQL Server to be ready, then verify:

```bash
docker compose ps
# mssql_dev should show status "healthy"
```

### Create the shared database

Run this once to create the database that all studies on this instance will share:

```bash
docker exec mssql_dev \
  /opt/mssql-tools18/bin/sqlcmd \
  -S localhost -U SA -P "YourStrong@Passw0rd" -C \
  -Q "IF DB_ID('omop_synth') IS NULL CREATE DATABASE omop_synth;"
```

### Connect from VS Code (optional sanity check)

Install the **mssql** VS Code extension (`ms-mssql.mssql`) and add a connection:

| Field | Value |
|-------|-------|
| Server | `localhost,1433` |
| Authentication | SQL Login |
| User | `SA` |
| Password | *(your MSSQL_SA_PASSWORD)* |
| Trust server certificate | ✅ |

You should see `omop_synth` in the database list.

## Step 3 — Download the OMOP Vocabulary from Athena

The OMOP vocabulary is the shared lookup that maps clinical codes (SNOMED, RxNorm,
ICD-10-CM, CPT-4, LOINC, …) to standard concept IDs. It is loaded once per SQL Server
instance and shared across all studies.

### 3a — Create an Athena account and select vocabularies

1. Go to [athena.ohdsi.org](https://athena.ohdsi.org) and create a free account.
2. Click **Download** in the top menu.
3. Select the following vocabulary bundles at minimum:

| Vocabulary | Why needed |
|------------|------------|
| **SNOMED** | Conditions, procedures, observations — the primary clinical vocabulary |
| **RxNorm** | Drug ingredients (required for drug exposure mapping) |
| **RxNorm Extension** | Drugs not yet in RxNorm (recommended) |
| **LOINC** | Lab measurements and observations |
| **ICD10CM** | Source codes for US diagnoses (mapped → SNOMED standard) |
| **CPT4** | US procedure codes — requires a UMLS API key (see Step 3b) |
| **HCPCS** | US procedure codes (outpatient) — recommended |
| **ICD10PCS** | US inpatient procedure codes — recommended |
| **Visit** | Visit type concepts (inpatient 9201, outpatient 9202, ED 9203) |
| **Gender** / **Race** / **Ethnicity** | Demographic concepts |
| **UCUM** | Units of measure |

4. Click **Download** (a `.zip` file, typically 2–5 GB).
5. Extract the zip. You will see files named `CONCEPT.csv`, `CONCEPT_ANCESTOR.csv`,
   `CONCEPT_SYNONYM.csv`, etc.
6. Move the **contents** of the extracted folder (not the folder itself) into
   `OMOP_Dev/omop_vocab/`:

```bash
# Example — adjust the extracted folder name to match your download
mv ~/Downloads/vocabulary_download_v5/* OMOP_Dev/omop_vocab/
```

After this step `OMOP_Dev/omop_vocab/` should contain `CONCEPT.csv` directly (not in
a subfolder).

### 3b — Rebuild CPT-4 codes (requires a free UMLS API key)

CPT-4 codes are licensed and not distributed directly by Athena. The Athena download
includes a small Java utility that fetches them from the NLM UMLS API.

**Get a UMLS API key (free):**
1. Register at [uts.nlm.nih.gov](https://uts.nlm.nih.gov) — select "Create an Account".
2. After approval (usually same-day), log in and go to your profile.
3. Copy your **API Key** from the profile page.

**Run the rebuild:**

```bash
cd OMOP_Dev/omop_vocab

# macOS / Linux
bash cpt.sh YOUR_UMLS_API_KEY

# Windows (Command Prompt — not PowerShell)
cpt.bat YOUR_UMLS_API_KEY
```

This appends CPT-4 rows to `CONCEPT.csv` (and creates `CONCEPT_CPT4.csv`). It
requires an internet connection and takes 5–15 minutes. Do not close the terminal
or interrupt the process — the script notes that interruption can corrupt
`CONCEPT.csv`.

> **No UMLS key yet?** You can proceed without CPT-4 initially and re-run the
> rebuild later. Procedures coded as CPT-4 will be unmapped until then. SNOMED-CT
> equivalents are available for most common procedures.

### 3c — Verify the vocabulary files

Before loading, confirm all required files are present:

```bash
ls OMOP_Dev/omop_vocab/
# Must include:
# CONCEPT.csv  CONCEPT_ANCESTOR.csv  CONCEPT_CLASS.csv
# CONCEPT_RELATIONSHIP.csv  CONCEPT_SYNONYM.csv
# DOMAIN.csv  DRUG_STRENGTH.csv  RELATIONSHIP.csv  VOCABULARY.csv
```

## Step 5 — Open in the dev container

1. Open VS Code.
2. **File → Open Folder** → select `OMOP_Dev/<your-study>/`.
3. Open the workspace root in VS Code and use the shared root-level dev container.
   Click **Reopen in Container**.
   *(If the notification does not appear: `Cmd+Shift+P` → **Dev Containers: Reopen in Container**)*
4. The first build compiles the Docker image (Java 17 + R 4.5 + system libraries).
   This takes **5–10 minutes** the first time; subsequent opens are under 30 seconds.
5. When the container is ready, the VS Code status bar shows the container name.
   Open a terminal (`Ctrl+`` `) — you should be in `/workspace`.

### Verify the environment

```bash
# Confirm you're inside the container
echo $IN_DEV_CONTAINER   # should print: true

# Confirm SQL Server is reachable
R -e "library(DBI); con <- DBI::dbConnect(odbc::odbc(), .connection_string = 'Driver=ODBC Driver 18 for SQL Server;Server=mssql_dev,1433;Database=omop_synth;UID=SA;PWD=YourStrong@Passw0rd;TrustServerCertificate=Yes;'); DBI::dbGetQuery(con, 'SELECT @@VERSION'); DBI::dbDisconnect(con)"
# OR use DatabaseConnector after workflow/01 installs packages (see Step 6)

# Confirm vocabulary files are mounted
ls /omop_vocab/CONCEPT.csv   # should exist
```

## Step 6 — Install R packages and verify the database connection

Run Step 1 of the workflow **from inside the container terminal**:

```bash
Rscript workflow/01_setup_synthea_etl_qc_env.R
```

This script:
- Activates the `renv` project library and restores all pinned packages (~5–10 min
  the first time; packages are cached in the container image layer on subsequent runs)
- Downloads and extracts the JDBC driver bundle to `drivers/`
- Opens a test database connection and prints the SQL Server version

If the connection test fails, check:
- The SQL Server container is running: `docker ps | grep mssql_dev`
- The `MSSQL_SA_PASSWORD` in `OMOP_Dev/.env` matches what you used in Step 2
- `MSSQL_HOST` inside the container is `mssql_dev` (set automatically by the devcontainer)

## Step 7 — Load the OMOP vocabulary into SQL Server

This is a **one-time step per SQL Server instance** (~30–60 minutes). Once loaded, all
studies on this machine share the same vocabulary schema — you never reload it between
studies or between Synthea runs.

```bash
Rscript ../infrastructure/scripts/setup_omop_vocab_schema.R --study-dir .
```

What the script does:
1. Creates the `omop_vocab` schema in `omop_synth` if it does not exist.
2. Creates all 10 OMOP CDM vocabulary tables in that schema.
3. Pre-grows the transaction log to 25 GB (required for `CONCEPT_ANCESTOR` — 75 M rows).
4. Bulk-loads all vocabulary CSVs from `/omop_vocab/` (mounted from `OMOP_Dev/omop_vocab/`).
5. Applies NULL corrections (`invalid_reason`, `standard_concept` — empty strings → SQL NULL).
6. Shrinks the transaction log back to ~1 GB.

**Disk space:** the loaded vocabulary occupies ~20–25 GB inside the Docker volume
(`mssql_dev_data`). Ensure your Docker Desktop has sufficient disk image size configured
(**Docker Desktop → Settings → Resources → Virtual disk limit**: set to ≥ 60 GB).

**If the script is interrupted:** re-run it. The script checks whether the `omop_vocab`
schema already has rows and exits early if so. To force a reload, drop the schema first:

```sql
-- Run in VS Code mssql extension or sqlcmd
USE omop_synth;
-- Drop tables in dependency order, then the schema
DROP TABLE omop_vocab.concept_ancestor;
DROP TABLE omop_vocab.concept_relationship;
DROP TABLE omop_vocab.concept_synonym;
DROP TABLE omop_vocab.drug_strength;
DROP TABLE omop_vocab.concept;
DROP TABLE omop_vocab.concept_class;
DROP TABLE omop_vocab.domain;
DROP TABLE omop_vocab.relationship;
DROP TABLE omop_vocab.vocabulary;
DROP SCHEMA omop_vocab;
```

```bash
# Check container status

docker compose logs -f mssql              # run from OMOP_Dev/

# Open interactive sqlcmd session
docker exec -it mssql_dev \
  /opt/mssql-tools18/bin/sqlcmd \
  -S localhost -U SA -P "YourStrong@Passw0rd" -C

# Stop the server (data persisted in Docker volume)
docker compose stop                        # run from OMOP_Dev/

# Full reset — removes ALL data including loaded vocabulary
docker compose down -v                    # run from OMOP_Dev/

# Rebuild the dev container image (after Dockerfile changes)
# Cmd+Shift+P → Dev Containers: Rebuild Container
```

## Troubleshooting

**Container exits immediately after `docker compose up`**
- The most common cause is a weak `MSSQL_SA_PASSWORD`. The password must have ≥ 8
  characters including uppercase, lowercase, a digit, and a symbol.
- Run `docker compose logs mssql` for the exact error.

**"Reopen in Container" does nothing or fails**
- Make sure the SQL Server container (`mssql_dev`) is running before reopening — the
  devcontainer joins its network.
- Confirm Docker Desktop is running and not in "paused" state.

**vocabulary load fails part-way through**
- The script is not atomic — a partial load leaves the schema in an indeterminate state.
- Drop the schema (SQL above), fix the root cause, and re-run the script.

**`/omop_vocab` is empty inside the container**
- Confirm `OMOP_Dev/omop_vocab/CONCEPT.csv` exists on the host.
- Confirm the study repo is cloned directly inside `OMOP_Dev/` (not deeper).
- Rebuild the container after fixing the path (`Dev Containers: Rebuild Container`).

**"Login failed for user 'SA'"**
- The password in `OMOP_Dev/.env` must exactly match what was used when the volume
  was first created. If they differ, run `docker compose down -v` and start over.

**Port 1433 already in use**
- Another SQL Server instance may be running locally.
  Check: `lsof -i :1433` (macOS/Linux) or `netstat -ano | findstr 1433` (Windows).
- Set `MSSQL_PORT=1434` in `OMOP_Dev/.env` and update `config.R` `sql_server_port`.
